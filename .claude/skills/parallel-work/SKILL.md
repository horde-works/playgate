# Параллельная работа: две машины и соседние агенты

Над этим репозиторием одновременно работают **две машины** и **несколько
сессий на каждой**. Почти всегда в рабочем дереве лежит чужая незакоммиченная
работа, а `origin` уезжает вперёд посреди твоей задачи. Это норма, а не авария.

Соседние плейбуки (читать в дополнение, не вместо):

- **git в общем дереве, запрещённые команды, отделение своей поломки от чужой**
  — `games/make-a-mess/docs/shared-tree-discipline.md`. Он владеет темой
  целиком; здесь она не пересказывается;
- **как получить наблюдение** (запуск, кадр, гигиена браузера) —
  `games/make-a-mess/docs/run-and-verify.md`;
- **протокол машин и список принятых красных тестов** — `CLAUDE.md` в корне.

| Адрес | `100.108.230.70` | `100.74.187.80` |

| Память / диск | 40 ГБ / 170 ГБ | 8 ГБ / около 5 ГБ |
| Рабочая копия | `C:\Users\IgorKirisyuk\cursor\playgate` | `~/cursor/playgate` |

Связь — SSH поверх Tailscale. Вход на Windows ведёт **не в Windows напрямую, а
в WSL-дистрибутив `Debian`**: штатный windows-sshd не умеет строить токен для
Entra-учётки (`AzureAD\...`, ошибка 1355) и потому отключён. Внутри WSL обёртка
`winrun` переносит команду в нативный windows-процесс, поэтому штрафа `/mnt/c`
на сборке нет.

## 2. Куда отправить задачу

Деление идёт **по весу задачи, а не по ролям машин**. Обе машины полноценно
правят код.

На **Windows** уходит всё длинное и тяжёлое: полный прогон, `next build`,
`next dev` со съёмкой кадров, широкие правки на много файлов, аудиты по всем
сценам, несколько параллельных worktree.

На **Mac** остаётся работа поуже: проектирование, ревью, документы, точечные
правки. Там 8 ГБ памяти и почти забитый диск, поэтому `npm ci`,
`npm run build`, полный `npm test` и `next dev` локально не запускают.

**Mac не отказывается от тяжёлого, а передаёт его.** Отказ «у меня не хватит
памяти» — неверный ответ; верный — отправить на Windows и дождаться.

## 3. Как передать работу

### Команда на Windows

```
ssh igor@100.108.230.70 "winrun npm test"
ssh igor@100.108.230.70 "winrun npx tsc --noEmit"
```

`winrun` выполняет команду в главном чекауте Windows-копии. Исходник обёртки —
[`tools/winrun`](../../../tools/winrun); **работает не он**, а установленная
копия вне git, в `/usr/local/bin/winrun` внутри WSL. Правка в репозитории не
меняет ничего, пока её не скопируют руками; в шапке файла есть команда установки
и сверка `cmp`.

**В worktree — только через `PLAYGATE_REPO`.** По умолчанию `winrun` уходит в
главный чекаут, а не туда, где лежит твоя задача:

```
ssh igor@100.108.230.70 "PLAYGATE_REPO='C:\Users\IgorKirisyuk\cursor\playgate-wt-hx6' winrun npm test"
```

Путь — в windows-форме; прямые слэши (`C:/Users/...`) тоже приняты и удобнее,
потому что переживают слои шеллов без экранирования. `/mnt/c/...` отвергается, а
не угадывается. Раньше рубильника не было, и прогон из worktree-задачи проверял
ЧУЖОЕ дерево, возвращая зелёный, — тот же класс обмана, что в §4, только зашитый
в инструмент.

**Ты уже на Windows?** Тогда никакого `ssh` — зови `winrun` напрямую. Он дверь из
WSL, а не обёртка, нужная локально. Агент на Windows, рефлекторно взявший
рецепт выше, уходит по ssh на собственную машину и попадает в главный чекаут,
сбежав из своего worktree, — §4 через инструкцию §3. (Сейчас это ещё и просто
падает: в `known_hosts` Windows лежит устаревший ключ от отключённого
windows-sshd.)

**Выход 2 значит «до PowerShell не дошло». Читай stderr, он скажет что именно.**
Не «неверный путь»: тот же код дают несуществующий каталог, `/mnt/c`-форма и —
чаще всего — метасимвол, умерший в `sh` ещё до PowerShell.

**Коды возврата.** `exit N` самого PowerShell доходит (`winrun exit 7` → 7), а вот
код нативного процесса сплющивается (`winrun cmd /c exit 7` → 1). Практическое
правило: не ветвиться на конкретных кодах, различать только 0 / не-0 / 2.

### Целая задача на Windows

```
ssh igor@100.108.230.70 "winrun claude -p \"'do the thing, in ASCII'\""
```

Форма кавычек здесь не украшение, и «очевидный» вариант с одинарными кавычками
НЕ работает. `winrun` склеивает аргументы через `$*` в одну строку `-Command`
**без перекавычивания**, поэтому кавычки для PowerShell обязаны дожить до него
литералами — через твой шелл и через удалённый. Замерено:

| что приходит на sshd | что видит PowerShell |
|---|---|
| `winrun echo 'hello'` | три отдельных аргумента — кавычки съедены удалённым шеллом |
| `winrun echo "'hello'"` | одна строка ✓ |
| `winrun echo "'привет'"` | `??????` |

Отсюда правила письма на ту сторону: **только ASCII** (кириллица уходит из шелла
валидным UTF-8 и приходит вопросительными знаками), **без апострофов** внутри
(ломают разбор строки), **одной строкой** (перевод строки разбирается как новая
команда PowerShell). Это тот же закон, что для `.ps1` в ASCII из `CLAUDE.md`.

### Два разных слоя кавычек — не перепутать

Полезная нагрузка проходит через POSIX `sh` **до** PowerShell, поэтому слоёв два,
и правила у них разные.

**Слой 1, кавычки для `sh`.** Любой метасимвол — `( ) $ | & ; < >` и обратная
кавычка — съедается, если payload не закавычен целиком. Одно правило покрывает
всё: **оборачивай всю PowerShell-нагрузку в двойные кавычки.**

| написано | что вышло |
|---|---|
| `winrun (Get-Location).Path` | `sh: Syntax error`, выход 2 |
| `winrun "(Get-Location).Path"` | ✓ `C:\Users\...\playgate` |
| `winrun echo $PSVersionTable` | переменную съел `sh` → ошибка параметра, выход 1 |
| `winrun "$PSVersionTable.PSVersion"` | ✓ `5 1 26100 8875` |
| <code>winrun git status \| head -2</code> | труба отработала в `sh`, а не в PowerShell |

**Слой 2, кавычки внутри PowerShell.** Вот здесь апострофы фатальны, здесь же
живёт форма `\"'...'\"` для `claude -p`.

Поэтому пример с worktree выше — `PLAYGATE_REPO='C:\...'` — не противоречит
правилу «без апострофов»: это кавычки СЛОЯ 1, они законны. Запрет на апострофы
относится к содержимому PowerShell-нагрузки, и отдельно `winrun` жёстко отвергает
апостроф внутри самого `PLAYGATE_REPO`.

На Windows учётные данные лежат файлом, поэтому headless-агент там работает.
Туда передают не только прогоны, но и **задачи по коду целиком** — они как раз
тяжелее и длиннее.

**В WSL нет node.** Передняя дверь — чистый POSIX `sh`; резолверы и скрипты на
node там не запускаются, они живут за `winrun`, уже на windows-стороне.

**Дистрибутив называть явно: `wsl -d Debian`.** Дистрибутив по умолчанию — не
Debian, `winrun` в нём отсутствует, а `/etc/hostname` у него **тот же
`igorki-primary`**. То есть проверка «я там, где надо?» по имени хоста проходит
в ЧУЖОМ дистрибутиве, и агент видит `command not found`, решая, что сломана
установка. Это же и есть живой пример, почему машину определяют пробой, а не
именем.

**MSYS2/Git Bash портит аргументы, похожие на путь.** Проверка WSL из
Bash-инструмента возвращает убедительный ложный отрицательный: замечено, как
`origin/fix/…:.gitattributes` приехало `origin\fix\…;.gitattributes` — подменены
`/`→`\` и `:`→`;` внутри git-рефа. Триггер — «похоже на путь», а не конкретные
символы. Лечится одной строкой, и запрещать Bash-инструмент не нужно:

```sh
export MSYS2_ARG_CONV_EXCL='*'
```

### Разговор с агентом на Mac

Обратное **невозможно напрямую**: на Mac учётные данные в Keychain, недоступном
неинтерактивной сессии, и `claude -p` по SSH падает с `Not logged in`. Правка
списка разделов Keychain (`security set-generic-password-partition-list`) эту
проблему НЕ решает — проверено, остаётся `errSecInteractionNotAllowed`. Не
тратить на это время.

Вместо этого работает почтовый ящик. Сторож `~/bin/mac-agent-watcher.sh`
запускается **из Terminal.app** (не по SSH — в этом весь смысл, процесс должен
унаследовать GUI-сессию):

```
screen -dmS macagent ~/bin/mac-agent-watcher.sh
```

Дальше обмен файлами:

```
scp вопрос.txt kirisyuk@100.74.187.80:.agent-mailbox/ask.txt
ssh kirisyuk@100.74.187.80 'cat ~/.agent-mailbox/answer.txt'
```

Перед новым вопросом удалять старый `answer.txt`, иначе прочитаешь прошлый
ответ. `~/.agent-mailbox/watcher.log` показывает, взят ли вопрос в работу.
Сторож не переживает перезагрузку — если ответа нет и лог молчит, он просто не
запущен.

**Что писать в письме.** Агент на той стороне не видит твоего контекста:
он не знает, что ты уже сделал, на каком ты коммите и почему спрашиваешь.
Письмо без этого возвращает вежливую пустоту. Давать: текущий коммит, что уже
проверено и чем, что именно нужно от него, и чего делать НЕ надо.

## 4. Главная ловушка: рабочих копий две

`winrun` работает в файлах Windows, а не в твоих. **Незапушенная правка для
него не существует** — прогон пройдёт по старому коду и вернёт зелёный, ничего
не проверив. Это самый дорогой способ обмануть себя в этой схеме.

Перед передачей тяжёлого прогона: закоммитить, запушить, на той стороне
`git pull`. Если прогон нужен по незакоммиченному — гнать его на своей машине
или не гнать вовсе.

### Как доказать, что прогон случился там, где ты думаешь

«Сработало» — не наблюдение. Доказательство собирается из независимых сигналов
и **обязательно из отрицательного контроля**:

```
winrun "(Get-Location).Path"           # оболочка
winrun git rev-parse --show-toplevel   # что думает git
winrun cmd /c cd                       # нативный дочерний процесс, не только оболочка
winrun "Get-Content marker.txt"        # маркер, который есть ТОЛЬКО в целевом дереве
```

**Слэши перед сравнением нормализовать.** `git rev-parse` отдаёт прямые, а
PowerShell и `cmd` — обратные; как строки они не равны, и агент прочтёт это как
доказательство чужого дерева.

**Отрицательный контроль ставить на ДРУГОЙ СУЩЕСТВУЮЩИЙ каталог**, обычно на
главный чекаут. Неверный путь тут не годится: `winrun` отвергает его выходом 2
ещё до запуска, и сравнивать становится нечего — так проверяется срабатывание
защиты, а не отсутствие маркера. Контроль без этой оговорки — единственный шаг,
отделяющий доказательство от самоуспокоения, — сам не работает.

### Свои пути — не прибивать

Абсолютный путь домашнего каталога одной машины делает файл мёртвым на второй,
и молча. Это уже случалось семь раз: шесть черновиков в корне репозитория
импортировали модули по маковому пути и на Windows не запускались вовсе, плюс
документ ссылался на картинку в `~/Downloads`. Сторож — `tests/portable-paths`.

Образец, как надо, в репозитории есть: `scripts/object-lab-capture.mjs` ищет
Chrome через переменную окружения, затем список кандидатов ОБЕИХ платформ с
`existsSync`. **Проба и переопределение, а не «определи машину и разветвись»:**
определение машины опирается на редактируемую конфигурацию (имя хоста в WSL
наследуется от Windows лишь до первой правки `/etc/wsl.conf`), а проба — на факт.

## 5. Две сессии на одной машине

Разводить по **подсистемам**, а не по принципу «кто успел»: мир / транспорт /
жители / разрушение / окружение. Пересечение по файлу — источник половины
потерь.

Когда нужна изоляция, каждой сессии свой worktree:

```
git worktree add ../playgate-<задача> <ref>
```

Помнить: `node_modules` между worktree не разделяются, каждому нужен свой
`npm ci` (около 0.5 ГБ). На Windows это терпимо, на Mac — нет.

Всё, что касается `git` в общем дереве — запрещённые команды, снятие baseline,
один файл на двоих, откат чужой правкой — в
`games/make-a-mess/docs/shared-tree-discipline.md`. Там же объяснено, чем
оплачен запрет на `git stash`.

## 6. Приём чужой работы

1. `git fetch`, посмотреть, что приехало: `git diff --stat <было>..<стало>`.
2. Свои коммиты ставить **поверх** через `git rebase origin/main`, а не
   вливать встречным merge.
3. Прогон после слияния обязателен, если пришёл код. Если пришли только
   документы — не обязателен, и честнее сказать об этом, чем гонять зря.
4. Сверять не «зелено ли», а **тот ли набор красных**. Поимённый список
   принятых красных — в `CLAUDE.md`. Любой не из списка — регрессия.
5. Число тестов растёт с каждым коммитом: сравнивать имена, а не счётчики.

## 7. Взаимные помехи, которые выглядят как баги

- Широкий `pkill -f headless` убивает браузеры соседних агентов
  (`run-and-verify.md`).
- Не мерить FPS, когда рядом идёт чужой прогон или сборка
  (`performance-lessons.md`).
- Не гонять сборку параллельно с тестами: тест рендера страницы делает
  собственный production-рендер в тот же каталог.
- Ошибки вида «не воспроизводится у меня» на разных машинах чаще всего
  платформенные, а не случайные. Уже ловили: загрузчики скиллов разной
  строгости к YAML (скилл терял все триггеры на одной машине и грузился на
  другой), `sips` вместо кроссплатформенного инструмента, пути Chrome без
  проверки существования, тайпчек, уходящий в `out/`.
